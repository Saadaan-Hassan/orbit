# ADR-001: Authenticated loopback sidecar and paired browser extension

- **Status:** Accepted
- **Date:** 2026-09-06
- **Deciders:** Orbit maintainer
- **Related roadmap tasks:** `SEC-002`, `SEC-003`, `SEC-004`

## Context

Orbit currently runs a FastAPI sidecar on a fixed loopback port. The desktop
webview and the browser extension can call it without caller authentication,
and its CORS policy is broad. A loopback address only limits network routing;
it does not establish which local process, website, or extension made a
request. Any process running as the user can connect to the port, and a website
or extension may be able to cause a browser request under some configurations.

CORS is a browser response policy, not an authentication mechanism: it does not
stop non-browser clients and it is enforced only after a request reaches the
server. Private Network Access is a browser feature with incomplete and evolving
coverage, not an authorization control. A fixed port or an undocumented route
is obscurity, not authentication.

The desktop application must continue to use a loopback sidecar, and the
extension needs a stable address rather than discovering a new random port on
each launch. The sidecar therefore needs explicit, scoped credentials.

## Decision

### Network endpoint and port ownership

The sidecar will bind only to `127.0.0.1:47821`. Orbit deliberately keeps this
stable port while the extension is supported. It will not choose a random port:
a random port would require an unauthenticated discovery mechanism or a new
extension-native transport, neither of which exists today.

The stable port is never the credential. The desktop and extension credentials
below protect it. At startup, Rust must not run a broad command such as
`lsof | kill -9` or kill whichever process owns the port. It may terminate only
a child process it created and still owns. If the port is occupied, or the
process answering `/health` does not prove knowledge of the current app-session
credential, Orbit fails closed with an actionable “local service unavailable”
state. It must not connect to, kill, or trust the occupant.

### Credentials and scopes

Orbit uses two independent bearer credentials. They are opaque, at least 256
bits from the operating-system CSPRNG, and encoded with base64url without
padding. They are sent only in an `Authorization: Bearer <token>` header; never
in a URL, query string, cookie, command argument, or request body.

| Credential | Issuer and lifetime | Storage/delivery | Scope |
|---|---|---|---|
| App-session token | Generated by the Rust/Tauri process for every sidecar start; invalidated on restart | Rust passes it to its child sidecar only as `ORBIT_LOCAL_API_SESSION_TOKEN` in the child environment. The webview obtains it only through a Tauri command and retains it only in the shared API module's memory. | Every desktop-sidecar route, including the minimal authenticated health check. |
| Extension token | Created only after explicit user pairing; remains valid until revoked, a full wipe, or explicit re-pairing/replacement | The extension background service worker stores the token in `chrome.storage.local`. The sidecar persists only a SHA-256 hash, paired extension ID, scope, creation time, and revocation state. | `POST /capture` only; no settings, recall, memory, AI, feedback, delete, or health access. |

The session token must not be persisted. It must not appear in application source,
Tauri command arguments, URLs, console/access logs, crash reports, analytics,
clipboard, `localStorage`, IndexedDB, or error messages. The sidecar must redact
the `Authorization` header and captured request bodies from error and access
logging. Environment delivery avoids command-line disclosure, but is not claimed
to protect against malware with the same user's OS privileges; a fully compromised
user account is outside this local API boundary.

The webview must use one `orbitApiFetch` wrapper. It lazily gets the current
session credential through the Tauri bridge, keeps it in a module-private
variable, attaches the authorization header, and clears/reacquires it after a
sidecar restart or a 401 response. Direct `fetch` calls to the local API are not
permitted after `SEC-003`. Tauri capabilities must restrict the token-returning
command to Orbit's main application window.

### Explicit extension pairing

Pairing is a user-authorized bootstrap, not extension auto-discovery:

1. The desktop app creates a one-time pairing code containing at least 128 bits
   of CSPRNG entropy, displays it to the user, and stores only its hash in memory.
2. The code expires after five minutes, is consumed after one successful use,
   and is invalidated after five failed attempts.
3. The user enters it into the extension's own pairing UI. The extension sends
   the code to the local pairing endpoint from its background worker, never from
   a content script.
4. The sidecar validates the code and the caller's syntactically valid Chrome
   extension origin, then returns one new extension token once. It stores the
   extension-token hash and exact extension ID with capture-only scope.
5. The extension stores the token only in its background-worker storage. It
   must never expose it to web pages, DOM content, content scripts, URLs, logs,
   or analytics.

The pairing endpoint accepts only a pending one-time code and cannot read Orbit
data. A code is an authorization secret: it is not copied to logs, support
messages, screenshots, or URLs. A stolen bearer token can be replayed, so
short-lived app tokens, one-use pairing codes, narrow extension scope, stored
hashes, and revocation limit the exposure; bearer authentication cannot make a
stolen valid token non-replayable.

The app exposes a paired-extension management view. Revocation deletes the
stored hash/allowlisted origin immediately. Subsequent extension requests return
401 and the extension must show that pairing is required; it must not silently
retry with a new token. Full local-data wipe revokes all extension pairings.

### Origin and CORS policy

Authentication is required even for an allowed origin. The only desktop origin
allowed in a production sidecar is exactly `tauri://localhost`, which is the
Tauri custom-protocol origin used by Orbit's production macOS webview. `SEC-003`
must add an integration test that proves the released webview uses this exact
origin before release.

Each paired extension has one exact allowed origin:

```
chrome-extension://<paired-extension-id>
```

`<paired-extension-id>` is the 32-character Chrome ID recorded during pairing,
not a wildcard and not an arbitrary `chrome-extension://` origin. The sidecar
returns `Access-Control-Allow-Origin` only when an incoming origin exactly equals
`tauri://localhost` or an active paired extension origin for that route. It sends
`Vary: Origin`, permits only the required methods/headers, and does not use
cookies or CORS credentials. Unknown, malformed, revoked, or unpaired origins
fail preflight and request validation.

`/health` has no CORS purpose: Rust performs the startup check itself with the
app-session bearer token. It returns only a minimal readiness result and no
version, path, setting, provider, or data information. The extension cannot call
it.

### Startup, rotation, and restart flow

```text
Tauri/Rust (trusted process)
  |  generate new app-session token from OS CSPRNG
  |  pass token through child environment only
  v
FastAPI sidecar on 127.0.0.1:47821
  |  authenticated minimal /health response to Rust
  |<-------------------------------------- Rust health request + bearer token
  |
  |  exact tauri://localhost origin + app-session token
  v
Orbit webview -- Tauri bridge --> module-private orbitApiFetch

Chrome extension background worker
  |  one-time code entered by user; receives capture-only token once
  |  exact chrome-extension://<paired-extension-id> origin + token
  v
FastAPI POST /capture only
```

On each app/sidecar restart, Rust generates a new app-session token and starts
a fresh authenticated readiness check. The webview discards its cached token and
obtains the replacement only through the shared wrapper. Existing extension
tokens remain valid across a normal desktop restart because they are independent
pairing credentials; they never gain desktop scope. A stale sidecar that lacks
the new session token fails the readiness check and is not used.

## Threat model and limits

| Threat | Required response |
|---|---|
| Hostile local process | Cannot use sensitive routes without a token; occupied-port/auth mismatch fails closed. Same-user malware can still compromise that user's environment and is not solved by a loopback API token. |
| Malicious website | Has no valid bearer token; its origin is not allowlisted. CORS/PNA are defense in depth, not the decision point. |
| Malicious extension | Has no authority unless explicitly paired; a paired extension is capture-only and can be revoked. |
| Token leakage | Avoid persistent/browser-page/log/URL delivery; rotate app token on restart, restrict extension scope, and revoke pairings. |
| Port squatting/stale sidecar | Bind to loopback, authenticate health, do not kill arbitrary PIDs, and show failure rather than trusting a process on the port. |
| Replay | Bearer tokens are replayable if stolen; one-time expiring pairing codes, app-session rotation, restricted scope, and revocation reduce the replay window. |

## Consequences

- The app, sidecar, and extension must be released as a compatible security
  change. A mismatched older component must fail closed with an update/re-pair
  instruction rather than silently fall back to unauthenticated access.
- The local API is no longer a general localhost service. New routes require an
  explicit scope decision and route-enumeration tests.
- The stable port remains convenient for the extension but is no longer trusted
  as an identity signal.
- The app must provide recovery UI for an occupied port, failed readiness check,
  and revoked extension pairing.

## Implementation mapping

| Roadmap task | Must implement this decision |
|---|---|
| `SEC-002` | Sidecar token configuration, constant-time authorization, route scopes, authenticated minimal health, strict host/origin/CORS validation, redacted logs, and route-enumeration tests. |
| `SEC-003` | Rust CSPRNG generation, environment-only sidecar delivery, authenticated readiness check, safe child ownership/port failure handling, Tauri capability, and the sole webview API wrapper. |
| `SEC-004` | One-time pairing UX/protocol, extension-token hash persistence, capture-only enforcement, dynamic exact paired-origin CORS, extension background storage, and revoke/re-pair management. |

## Alternatives considered

- **Loopback binding plus wildcard CORS:** rejected because neither authenticates
  callers.
- **A random loopback port:** rejected for the current extension architecture;
  it would move rather than solve discovery/authentication. It can be reconsidered
  only when the extension no longer depends on a stable local HTTP endpoint.
- **One shared static token in source/config:** rejected because it would be
  extractable from a public repository or installed client and cannot be revoked
  per installation or extension.
- **Use the app-session token in the extension:** rejected because it grants the
  extension all desktop API authority and rotates every restart.

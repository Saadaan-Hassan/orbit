# Orbit Threat Model

What Orbit defends against, how, and what it explicitly doesn't try to
defend against. Read [`ARCHITECTURE.md`](ARCHITECTURE.md) first for the
trust-boundary map this document assumes.

**Scope note:** Orbit is a local-first, self-build desktop app with no
maintainer-run infrastructure. The threats below are about a *user's own
machine and their own choices* (what to capture, which AI key to add), not
about defending a hosted service — because no hosted service exists.

## 1. Hostile web content

**Threat:** a malicious or compromised web page tries to get sensitive
content (credentials, tokens, personal data) into Orbit's stored memory, or
tries to exploit the capture path itself.

**Mitigations:**
- Page content is captured as inert text via `@mozilla/readability`
  (extension) or accessibility APIs (native) — never executed, never
  rendered.
- All captured text passes through pattern-based redaction before any disk
  write: `clipboard.rs` for clipboard content, `redaction_service.py` for
  browser-captured content, a shared Rust sanitizer (`ADR-003`) for
  everything else. Secrets (API keys, private keys, JWTs, credit
  card/SSN-shaped values, crypto addresses) become `[REDACTED:type]` before
  they ever touch SQLite.
- `AXSecureTextField` (password fields) is skipped unconditionally at every
  traversal depth in the on-screen capture path — never read, not even to
  redact.
- The user can exclude any domain or app from capture entirely
  (`services/exclusion_policy.py`).

**Accepted residual risk:** redaction is pattern-based and best-effort, not
a formal guarantee — a sufficiently unusual secret format could slip
through. Documented plainly in the privacy policy, not overclaimed.

## 2. Another local process on the same Mac

**Threat:** malware, another app, or a browser-based attacker tries to read
from or write to Orbit's local FastAPI backend (localhost:47821) to
exfiltrate memory data or inject events.

**Mitigations:**
- Every route requires a bearer token: a fresh 256-bit value generated by
  Rust once per app session, passed to the backend only via the spawned
  child process's environment — never written to a file, never sent to any
  webview global, never logged (`ADR-001`, `SEC-002`/`SEC-003`).
- Exact `Host` header validation (`127.0.0.1:47821` / `localhost:47821`
  only) and exact `Origin` validation (`tauri://localhost` in production,
  plus the Vite dev origin only in debug builds).
- Restrictive CORS: only specific methods/headers allowed, credentials
  never accepted via query parameters.
- `/health` itself requires the same token — even a liveness probe can't be
  used to fingerprint the app from an unauthenticated local process.
- Port-collision handling is deliberately conservative: if something else
  already holds port 47821, the app does not kill or trust an arbitrary
  process on it (the one narrow exception — a dev-mode helper that kills a
  process only if its exact command line matches Orbit's own backend
  invocation, so iterative `pnpm tauri dev` restarts don't get stuck on
  their own orphaned children — never applies to release builds or to a
  process it can't positively identify as its own).

## 3. The Chrome extension, if compromised or malicious

**Threat:** a malicious or compromised version of the extension tries to
read arbitrary app data, or another extension impersonates it.

**Mitigations:**
- The extension never receives the app's own session token. It gets a
  separate, capture-only token issued via a short-lived (5-minute), one-use
  pairing code the user must explicitly generate from the authenticated
  desktop UI (`SEC-004`).
- That token is scoped to exactly one route (`/capture`) and one exact
  extension ID (`chrome-extension://<32-char-id>`) — it cannot read, only
  write, and only to that endpoint.
- Revoking pairing (or a full data wipe) immediately invalidates the token;
  only its hash is stored server-side, never the raw value.
- All state lives in `chrome.storage.session` — never global variables that
  could leak across contexts.

## 4. The AI provider (Groq, Voyage AI)

**Threat:** the provider itself, or someone who compromises the connection
to it, sees more than intended, or the provider is used as a channel to
exfiltrate data the user didn't mean to send.

**Mitigations:**
- BYOK only — the user's own key, used directly over HTTPS to the
  provider's own API. No maintainer-run relay of any kind exists to add an
  additional party to this trust relationship.
- Only already-redacted content is ever sent (see §1) — the provider
  boundary applies the same sanitizer as the storage boundary, plus
  additional caps on field/request size (`PRIV-004`).
- With no personal key configured, the relevant feature fails immediately
  with no network request attempted — there's no fallback to silently
  degrade into sending data somewhere the user didn't opt into.
- `category = 'personal'` events are excluded from work-intent recall
  context before it's sent.

**Accepted residual risk, stated plainly in the privacy policy:** the
provider's own data-retention practice is outside Orbit's control. Groq
does not retain inference data by default; Voyage AI trains on submitted
data by default unless the user opts out on their own Voyage account.
Orbit cannot enforce either provider's policy — it can only avoid sending
more than necessary and disclose this honestly.

## 5. Dependency and build supply chain

**Threat:** a compromised dependency, or a compromised GitHub Action,
introduces malicious code into a contributor's build.

**Mitigations:**
- Every third-party GitHub Action referenced in CI is pinned to a full,
  reviewed commit SHA, not a mutable tag (`CI-002`).
- `actionlint` (structural) and `zizmor` (GitHub-Actions-specific security
  auditor — secret exposure, template injection, permission scope) both run
  clean against every workflow file.
- Dependabot watches every ecosystem in the repo (GitHub Actions, Cargo,
  `uv`, and each JS/TS workspace independently).
- A full dependency-license scan (`THIRD_PARTY_NOTICES.md`) found no
  copyleft-propagating or unknown/missing license across 582 Rust crates,
  ~40 Python packages, and every JS/TS workspace.
- Pull-request CI runs the full lint/typecheck/test suite for every
  workspace before merge (`CI-001`/`CI-002`).

**Explicitly out of scope:** there is no release/build/signing pipeline to
compromise (see `ARCHITECTURE.md`'s `Distribution model`) — every user
builds from source on their own machine, so there's no shared build
artifact whose compromise would affect more than one person at a time.

## 6. Local database theft (stolen or accessed Mac)

**Threat:** someone gets physical or remote access to the user's Mac and
reads `~/.orbit/` directly, bypassing the app entirely.

**Mitigations:**
- `~/.orbit/`, the SQLite database (+ WAL/SHM), Qdrant's storage directory,
  the device ID, and the onboarding marker are all set to owner-only
  permissions (`0700`/`0600`) without following symlinks (`ADR-004`).
- Secrets never reach the database in plaintext — redaction happens before
  the write, not after (see §1).
- The macOS Keychain (not SQLite, not a config file) holds any BYOK
  provider key.

**Accepted residual risk, stated plainly:** Orbit does not encrypt its own
database at the application level. Protection against a stolen, unlocked
Mac relies entirely on FileVault (macOS's own full-disk encryption), which
the privacy policy recommends explicitly. This is a deliberate scope
decision, not an oversight — application-level encryption of a local SQLite
database a single user already controls the disk-level encryption for adds
complexity without a clear threat it uniquely addresses.

## 7. Maintainer-account compromise

**Threat:** the maintainer's GitHub account, or some other account they
control, is compromised.

**Mitigations:**
- No maintainer-run infrastructure exists for an attacker to pivot into —
  no Cloudflare Worker, no hosted backend, no release pipeline. The
  Cloudflare Worker that once existed has been deleted entirely, not just
  had its credentials rotated.
- The only maintainer-controlled assets left are: the GitHub source repo
  itself, and (by the maintainer's own choice) a Vercel deployment of the
  fully static landing site, which has no backend, database, or secrets of
  its own to steal.
- The GitHub repo itself is hardened against this: branch/tag protection
  rulesets (no force-push or deletion, even for the owner), secret
  scanning with push protection, and Actions restricted to an explicit
  allowlist of the exact actions the CI workflows use — all reducing the
  blast radius of a compromised maintainer account.

## Non-goals

Stated explicitly so they aren't mistaken for oversights:

- **Not defending against a user who chooses to send their own data
  somewhere.** BYOK means the user decides to trust a provider with their
  own key; Orbit's job is to not send *more* than the feature requires and
  to be honest about what's sent, not to prevent the user's own informed
  choice.
- **Not a multi-user or enterprise access-control system.** Orbit assumes
  one user, one Mac, one local account. There is no concept of shared or
  delegated access.
- **Not resistant to a fully compromised OS kernel or root-level attacker
  on the same machine.** If an attacker already has root, or has
  compromised the kernel, no userspace application-level control can
  meaningfully defend against them.
- **No formal cryptographic audit has been performed.** The security work
  in this repo (see `docs/adr/` for the individual decisions) is a
  systematic engineering hardening pass, not a third-party penetration
  test or formal verification.
